### Sprint A — Critical Fixes (P0)

#### SEC-01: Live service-role key in local `.env`
- **Problem:** `.env` contains `VITE_SUPABASE_SERVICE_KEY=<live JWT>` — unused by any code, but a `VITE_`-prefixed name means Vite would inline it into the browser bundle the instant any future code references it.
- **Root cause:** Leftover from before the CRIT-1 fix (per AUDIT_LOG.md, the original service-key-removal fix changed the *consuming code* to use an Edge Function, but never cleaned up this local env file).
- **File(s):** `.env` (not tracked by git, local-only)
- **Fix:** Delete the `VITE_SUPABASE_SERVICE_KEY` line from `.env` entirely — it serves no purpose since all privileged operations already go through Edge Functions reading `SUPABASE_SERVICE_ROLE_KEY` server-side. Additionally, **rotate this key in the Supabase dashboard** (Settings → API → service_role → Reset), since its value was displayed in this audit's tool output and is now present in conversation history.
- **Test:** After rotation, confirm `admin-reset-password`, `notification-worker`, and other Edge Functions still work (they read the rotated key fresh from Supabase's own secret store, unaffected by the local `.env` change).
- **Risk:** Low (the line removal is a no-op for app functionality; key rotation requires updating the Supabase Edge Function secrets if they were ever manually pinned — verify they read live from `Deno.env.get`, which they do per Phase 2 audit).
- **Estimated effort:** XS (5 minutes — delete line + rotate key in dashboard)

#### SEC-02a: PartsInventory permission bypass
- **Problem:** `canAdd`, `canEdit`, `canAdjust` in `PartsInventory.jsx` use `canDo('create') || currentUserRole === ROLES.MANAGER` — the hardcoded `||` clause grants Manager/Technician access regardless of what an admin sets via Edit Permissions.
- **Root cause:** Likely written before granular `parts` permissions existed in `ROLE_DEFAULT_PERMISSIONS`, then never cleaned up after `canDo('create')`/`canDo('edit')` were added alongside it.
- **File(s):** `src/pages/PartsInventory.jsx:346-354`
- **Fix:**
  ```js
  // Before:
  const canAdd = canDo('create') || currentUserRole === ROLES.MANAGER
  const canEdit = canDo('edit') || currentUserRole === ROLES.MANAGER
  const canAdjust = canAdd || currentUserRole === ROLES.TECHNICIAN || canDo('adjust_stock')

  // After:
  const canAdd = canDo('create')
  const canEdit = canDo('edit')
  const canAdjust = canDo('adjust_stock')
  ```
  `canDo()` already bypasses for `super_admin`/`admin` and correctly checks `currentUserPermissions.parts[action]` for everyone else — since `ROLE_DEFAULT_PERMISSIONS.manager.parts` already has `create: true, edit: true` and `ROLE_DEFAULT_PERMISSIONS.technician` (verify exact default) covers `adjust_stock`, removing the hardcoded OR does not change default behavior for unmodified roles — it only removes the ability to override.
- **Test:** As admin, open Edit Permissions for a Manager test user, uncheck "Create" under Parts Inventory, save. Log in/preview as that user — the "Add Part" button should now be hidden. Re-check the box — button reappears.
- **Risk:** Low (default-permission behavior is unchanged; only removes an override-bypass)
- **Estimated effort:** XS (10 minutes + manual verification)

#### SEC-02b: Invoices permission bypass
- **Problem:** `isManager`/`isTech`/`isViewer` in `Invoices.jsx` are hardcoded role booleans that gate `canChangeStatus`, `canEdit`, and the "New Invoice" button — never consulting `canDo('invoices', ...)`. The granular Invoice permissions in Edit Permissions are completely decorative.
- **Root cause:** Same pattern as SEC-02a — Invoices predates or was never migrated to the granular `canDo()` system for this specific page.
- **File(s):** `src/pages/Invoices.jsx:535-537,580,753,804,915-916,1017-1018`
- **Fix:** Add a local `canDo(action)` helper (matching the pattern already used in `RMATickets/index.jsx`, `TicketDrawer.jsx`, etc.):
  ```js
  const canDo = (action) => {
    if (currentUserRole === ROLES.ADMIN || currentUserRole === ROLES.SUPER_ADMIN) return true
    return currentUserPermissions?.invoices?.[action] === true
  }
  ```
  Replace:
  - `isViewer` gates (lines 753, 804) → `!canDo('view')` is wrong since viewers should still see the list; replace with `canDo('create')` directly for the create-gated actions (the "New Invoice" button and the empty-state CTA), not a viewer-exclusion pattern.
  - `canChangeStatus = isManager` (line 915, 1017) → `canChangeStatus = canDo('edit')` (status changes are an edit action)
  - `canEdit = isManager` (line 916, 1018) → `canEdit = canDo('edit')`
  - Leave `isTech` (line 536, used at 580/590 for a tech-specific filtered view, not a permission gate) — that's a legitimate UX branch, not a security check, no change needed.
- **Test:** Same pattern as SEC-02a — toggle Invoice "Edit" permission off for a test Manager via Edit Permissions, confirm the Invoices page now hides edit/status-change actions for that user (test via Preview-as-user, FT-09).
- **Risk:** Medium (touches more call sites than SEC-02a; verify `currentUserPermissions` prop is actually passed into `Invoices.jsx` from `App.jsx` — confirm before assuming `canDo` has data to read)
- **Estimated effort:** S (30-45 minutes incl. verification)

#### CI-01: `lint:ci` fails — CI is broken
- **Problem:** `npm run lint:ci` (the exact command `.github/workflows/ci.yml` runs) fails with 2 errors + 11 warnings. Any push/PR to `main` right now would fail CI at the lint step.
- **Root cause:** `requestAnimationFrame`/`cancelAnimationFrame` are missing from `eslint.config.js`'s `globals` object — a config gap (the code in `BarcodeScanner.jsx` is correct browser API usage; ESLint just doesn't know these globals exist). The 11 warnings are separate, pre-existing `no-unused-vars`/`react-hooks/exhaustive-deps` issues across 9 files that also fail because `lint:ci` uses `--max-warnings 0`.
- **File(s):** `eslint.config.js` (config fix) + 9 files with warnings (see docs/archive/SYSTEM_AUDIT_REPORT_20260617.md Phase 1 for the full list)
- **Fix:**
  1. Add to `eslint.config.js`'s `globals` object: `requestAnimationFrame: 'readonly', cancelAnimationFrame: 'readonly'` — this alone fixes both errors.
  2. For the 11 warnings, either fix each (remove unused vars, add missing hook deps) or — if any are intentional — add a scoped `// eslint-disable-next-line` with a one-line justification comment. Do not blanket-disable the rules.
- **Test:** Run `npm run lint:ci` — should exit 0 with no output.
- **Risk:** Low for the globals fix. Low-Medium for the 11 warnings — `react-hooks/exhaustive-deps` fixes can change effect timing if not done carefully; verify each page still loads correctly after the fix (especially `Reports.jsx`, `TechCalendar.jsx`, `cp/AuditLog.jsx`, `cp/DataCleanup.jsx`, `cp/RMAConfig.jsx` which all have the missing-dependency warning).
- **Estimated effort:** S (config fix is XS/5 min; the 11 warnings collectively are ~1-2 hours with testing)
